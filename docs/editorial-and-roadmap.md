# 编辑标准与后续计划

写于 2026-10-08。这份文档交给接手后续工作的执行者（人或 AI 代理），说明三件事：还缺哪些人物图片、人物传记按什么标准写、项目接下来做什么。先读“开工前必读”，再按“任务清单”的顺序做。

## 开工前必读

### 运行与检查

```bash
npm install
npm run dev          # 本地预览，默认 http://localhost:5173
npm run check        # 类型检查 + 单元测试 + 构建，每次改动后必须通过
npm run test:e2e     # 33 项端到端检查，改动页面或数据后必须通过
node tests/production.mjs   # 针对 dist 的生产构建检查，需先 npm run build
```

端到端测试依赖 Playwright 自带的 Chromium。首次运行前执行 `npx playwright install chromium`。测试会重写 `docs/qa/` 下的截图和结果文件，这是预期行为，随改动一并提交。

### 不能破坏的原则

这些是站点的立身之本，优先级高于任何设计或内容上的改进：

1. **没有来源的关系，不画。没有核验的现状，不猜。未被覆盖的内容，留白。**
2. 每条事实记录、每个时间节点、每个传记章节都必须带 `sourceIds`，且能在 `src/data.ts` 的 `sources` 中解析到。
3. 历史任职不等于现任。关系的 `status`（`current` / `snapshot` / `historical` / `event` / `navigation`）是人工判定的，不要根据措辞自动推断，也不要为了画面好看而修改。
4. `datasetDate` 是版本日期，各条来源的 `verified` 是各自的核验日期。没有重新阅读过的来源，保留原核验日期。
5. 不使用 AI 生成的人物肖像。没有可用照片的人物用字母标识。

### 代码结构

| 文件 | 内容 |
|---|---|
| `src/data.ts` | 公司、人物、关系、事件、来源。事实的唯一出处 |
| `src/profiles.ts` | 人物传记章节与速览。与 `data.ts` 分开，便于审稿 |
| `src/main.ts` | 路由与全部页面模板 |
| `src/graph.ts` / `graph.css` | 关系图谱页 |
| `src/map.ts` / `map.css` | 首页关系地图。节点坐标是手工排的 |
| `src/style.css` | 最早的基础样式，4000 多行，多轮改版层层覆盖 |
| `src/home.css` `polish.css` `front.css` `refine.css` | 之后叠加的样式层，按 `main.ts` 里的引入顺序生效 |
| `vite.config.ts` | 构建时为每个颜色自动生成深色主题对应值 |

新增公司或人物时，必须在 `src/map.ts` 的 `mapLayouts` 里为它补上 `wide` 和 `tall` 两套坐标，否则单元测试会失败。

### 图片必须满足的条件

- **授权明确**：只接受 CC BY、CC BY-SA、CC0、公有领域，或权利人书面许可。首选 Wikimedia Commons。新闻图片社、公司官网、社交媒体上的照片，没有明确许可就不能用。
- **是本人的真实照片**。不接受 AI 生成、AI 修复或合成图像。
- **来源文件不做修改**。灰度、裁切、位置都用 CSS 处理，不改原图。CC BY-SA 的照片尤其如此。
- **规格**：JPEG，短边不低于 800px，文件不超过 300KB，脸部清晰且位于画面上半部分。
- 找不到符合条件的照片就保持字母标识，并在本文档里记下“已查找、未找到”，不要降低标准。

### 加一张照片要改的四处

1. 文件放到 `public/assets/<id>.jpg`。
2. 把 id 加进 `src/main.ts` 顶部的 `available` 数组。
3. 在 `docs/assets.md` 按现有格式登记：文件、摄影者与日期、来源链接、许可证链接。
4. 在 `src/main.ts` 的 `aboutPage()` 里 `asset-credits` 列表补一条署名。

脸部位置不合适时，在样式里加 `.portrait-<id> img { object-position: 50% 30%; }` 微调。这个类同时作用于大头像、圆形头像和地图节点，改完要在首页地图、人物索引、人物档案页三处都看一眼。

## 二、人物传记撰写标准

传记写在 `src/profiles.ts`，每人一个条目，包含 `facts`（速览）和 `chapters`（章节）。页面会在这些章节之后自动接上“公开记录中的角色”“沿着时间阅读”“人物资料来源”三章，这三章的内容来自 `data.ts`，不要在传记里重复。

### 结构

**速览 `facts`**：3 到 5 行，每行一个标签加一句话。常用标签依次为：出生、成长、教育、导师、竞赛、此前、现任、荣誉。没有可靠信息的行直接省略，不要写“不详”。

**章节 `chapters`**：按时间顺序，通常 4 到 6 章：

1. 早年与教育
2. 进入本行业之前的工作
3. 进入图谱所记录的机构的经过，以及在其中做了什么
4. 重大事件（如 2023 年 11 月的 OpenAI 董事会风波），只写与此人直接相关的部分
5. 之后的去向或其他职务
6. 公共立场与荣誉

章节标题用具体的名词，如“Bullfrog 与剑桥”“执掌 Y Combinator”，不要用“职业生涯（一）”这类编号式标题。

**篇幅**：每章 2 到 4 段，每段 60 到 200 字。全篇背景部分 1200 到 2200 字为宜。资料确实少的人物可以更短，不要为了凑字数而重复或发挥。

### 来源

- **优先原始资料**：公司公告、本人署名文章、论文、官方简历页、政府或奖项机构的公告。
- **现状**：目前 10 位人物的背景章节全部来自英文维基百科，来源标题里已注明“二手汇编，非原始资料”。这是过渡状态，目标是逐章替换为原始资料。
- 每章的 `sourceIds` 只列这一章实际用到的来源。一章用了两个来源，就列两个。
- 新增来源写进 `data.ts` 的 `sources`：`id`、`title`、`url`（必须 HTTPS）、`published`（有则写）、`verified`（实际打开核对的日期）。
- 媒体报道可以作为来源，但要在行文里写明是谁报道的，如“据路透社 11 月 21 日报道”。

### 行文

- **只写来源里有的事实**。不推断动机，不补充常识性背景，不写“众所周知”。来源没有写明年份的事，就不写年份。
- **每个职务都带时间**。写“2013 至 2016 年在 Tesla 担任 Model X 产品经理”，不写“曾在 Tesla 任职”。
- **不用现在时陈述未经核验的现状**。写“2021 年出任研究总监”，不写“现任研究总监”，除非有当前日期的来源。
- **归因要清楚**。评价性的内容必须写明出处，如“其维基百科条目认为”“《时代》周刊和 Vox 都把他称为”。不要把他人的评价写成本站的判断。
- **不做总结性的议论**。不写“这段经历为他日后的成功奠定了基础”这类句子。事实摆出来，读者自己判断。
- **集体成果不归于个人**。写“参与了 GPT-2、GPT-3 的研发”，不写“开发了 GPT-3”，除非来源明确如此。
- **引语**：短引语保留，放在中文引号里并给出译文；不确定原文措辞时改为转述。
- **与图谱数据一致**。传记里提到的任职，如果 `relationships` 里也有记录，日期和职务名称必须对得上。发现矛盾时先停下核对，不要让两处各说各话。

### 术语与格式

- 人名保留英文原文，不音译；`cnName` 字段已提供中文名。中国、日本、韩国人物用通行的汉字写法，如“李世石”“柯洁”。
- 机构名有通行中文译名的用中文（斯坦福大学、麻省理工学院、红杉资本），没有的保留英文（Y Combinator、Leap Motion）。
- 论文、文章、书名、游戏名用书名号并保留原文：《Machines of Loving Grace》。
- 日期写作“2023 年 11 月 17 日”；金额写作“4340 万美元”“10 亿美元”；外币注明币种。
- 中英文之间、中文与数字之间留一个半角空格。

### 不写什么

以下内容即使来源里有，也不写进传记：

- 婚姻、伴侣、子女、宗教、性取向、健康状况。唯一的例外是本人公开把它与某项职业决定联系起来，这时只写这层联系，不写细节。
- 个人财富、持股估值、薪酬。
- 政治捐款与党派立场。
- 诉讼、指控和未经裁决的争议。
- 来源日期晚于执行者自身能核实范围、且与站内现有记录冲突的说法。遇到这种情况记入下方“待定事项”，交给维护者决定。

如果维护者决定某一类信息应当呈现（例如政治捐款属于公共信息），要对所有人物统一适用，并在本节更新规则。

### 提交前自查

- [ ] 每一句都能在所列来源里找到对应内容
- [ ] 每个职务都有时间
- [ ] 没有推断、评价和总结性议论
- [ ] 与 `relationships`、`milestones` 里的日期和职务一致
- [ ] `npm run check` 通过

## 四、任务清单

按优先级排列。每项完成的标准是：改动通过 `npm run check` 和 `npm run test:e2e`，并在 README 的更新记录里加一段说明。

### 第一优先：内容的可信度

1. **逐句核对现有 10 篇传记**。打开每章所列来源，核对年份、金额、职务名称和引语。有出入的改正，查不到的删除。
2. **把维基来源换成原始资料**。逐章寻找公司公告、官方简历、论文、本人文章，替换或补充 `sourceIds`。全部替换完的人物，从阅读须知里去掉“二手汇编”的说明。
3. **补写 Brad Lightcap 和 Thibault Sottiaux 的传记**。这两位没有维基条目，需要从 OpenAI 官方页面、会议讲者简介、本人公开资料入手。资料不足时宁可只写两章。
4. **处理“待定事项”的第 1、2 条**，在维护者确认之后。

### 第二优先：图片

5. 按第一节的标准，为 7 位人物寻找有授权的照片。
6. 为 SSI 和 Thinking Machines Lab 确认是否有可用的官方标志。

### 第三优先：技术债

7. **合并样式**。`style.css` 加上后来的五层样式，同一个选择器被重写多次，后几层用 `#app` 提高优先级来压过前面。目标是整理成一套设计令牌（颜色、字号、间距）加按页面拆分的样式文件，删除失效规则。这是高风险改动，要分页面逐步做，每一步都对照 `docs/qa/` 的截图。
8. **深色模式逐页检查**。深色配色由构建时自动推导，只人工看过首页、公司页、图谱、时间线和一个人物页。需要逐页检查对比度，个别不合适的颜色用手写的 `light-dark()` 覆盖。
9. **深色模式的浏览器兼容**。`light-dark()` 需要 Chrome 123、Safari 17.5、Firefox 120 及以上，旧浏览器上颜色会失效。如需兼容，改为同时输出一个不带 `light-dark()` 的回退声明。
10. **无障碍检查**。按 WCAG 2.1 AA 过一遍：对比度、键盘可达、焦点可见、屏幕阅读器对首页地图和关系图谱的朗读顺序。
11. **字体与性能**。衬线字体是 WOFF 格式的完整字库，可转为 WOFF2 并按用字子集化。

### 第四优先：产品方向

12. **扩大深度档案**。目前只有 OpenAI 是深度档案，其余 8 家是精选概览。下一家建议 Anthropic 或 Google DeepMind，按 OpenAI 的标准补齐人物、治理关系、产品和时间线。
13. **补充人物**。Meta AI、xAI、DeepSeek、Microsoft 目前没有收录人物，首页地图上是孤立节点。
14. **真实网址**。现在用的是 `#/person/...` 形式的哈希路由，搜索引擎无法分别收录各页。可以改为真实路径并在构建时预渲染为静态页面。
15. **来源的可追溯性**。为每条来源保存一份存档链接（如 Internet Archive），防止原链接失效。
16. **更新机制**。目前是手工编辑的静态版本。可以加一个定期任务，检查来源链接是否仍可访问，并列出核验日期超过 90 天的记录。

## 五、给执行者的工作约定

- 一次只做清单里的一项，做完、测试通过、提交，再做下一项。
- 不确定某个事实时不要写，记入“待定事项”。
- 不要为了让测试通过而修改测试的断言。测试失败说明改动有问题；只有在设计或数据有意变更时才更新对应的断言，并在提交说明里写明原因。
- 每次提交后更新 README 的更新记录，写清楚改了什么、哪些没有核实。
- 改动人物或公司数据时，同步检查首页地图、图谱页、索引页、档案页、搜索五处的显示。
